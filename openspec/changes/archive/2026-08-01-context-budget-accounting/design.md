## Context

本次變更源自對 pi agent harness（earendil-works/pi）的設計研究。pi 是刻意極小化的單機 coding agent harness，其 system prompt 模板約 1.2 KB、只有七個工具（預設四個）、工具說明都是一句話等級，作者宣稱 system prompt 加工具定義合計低於 1000 tokens。

比對 Fleety 現況的量測結果：

| 項目 | pi | Fleety |
| --- | --- | --- |
| system prompt | 約 1.2 KB 模板 | 57,135 字元（protocol 25,343、rules 8,445、memory 13,397、policy 9,950）加 core memory |
| 工具數 | 7（預設 4） | 約 100（registry 共 108 個 spec） |
| 工具 schema 總量 | 低於 1 KB | 約 46 KB |
| 每次請求固定開銷 | 低於 1000 tokens | 約 30K tokens |
| token 計量 | 有 | 無 |

pi 的省錢機制中，工具漸進式載入與 system prompt 分層是收益最大的兩項，但都屬於大範圍重構。Fleety 已經有兩個現成的同類先例證明該模式可行：裝置端工具整組收在單一 `device_exec` 之後、MCP 伺服器工具整組收在單一 `mcp_call` 之後，兩者都不展開子工具 schema。skills 也已經做對了漸進式揭露，system prompt 完全不含 skill 內容，靠 `list_skills` 與 `use_skill` 按需載入。

因此本次刻意不做架構移植，而是先修掉三個獨立可驗證的缺陷，並補上量測能力，讓後續的漸進式載入提案有數字可以支撐與驗收。

三個缺陷中，第一項在研究過程中被確認為規格違規而非單純的效率問題：`instruction-file-injection` 規格的「Scenario: injection survives compaction」明文要求指令檔在壓縮後仍每回合存在，該規格描述正確，是實作沒有達成。

## Goals / Non-Goals

**Goals:**

- 讓 compaction 的字元預算只衡量真正可被壓縮的歷史區段，使門檻回復為有意義的閘門。
- 讓每回合重新注入的不可壓縮前言（當前時間、origin 前言、指令檔前言）原樣送達模型，恢復 `instruction-file-injection` 的規格符合性。
- 讓檔案讀取工具對同一份切片只回傳一種視圖，把工具結果字元預算留給實際內容。
- 讓三個模型供應商回報的 token 用量能被解析並在回合層級彙總，作為後續優化的驗收基準。

**Non-Goals:**

- 工具漸進式載入、system prompt 分層下沉為 skill：本次量測要支撐的下一步，需獨立提案。
- Anthropic 供應商與快取斷點：Fleety 目前沒有 Anthropic 供應商。
- 每 token 金額換算與費用表。
- 把用量寫進持久化事件流。
- 為 compaction 門檻新增環境變數。
- reflection 回合、goal 自動續轉、subagent 重付 system prompt 等其他開銷來源。

## Decisions

### 預算只計算可壓縮區段

字元預算的語意改為「可壓縮歷史的大小」，不再包含開頭不可壓縮的前言。理由：預算的目的是決定「歷史是否長到該摘要」，而 system prompt 與每回合重建的前言無論如何都會原樣送出，把它們算進來只會讓門檻恆真、使門檻失去意義。

替代方案是把門檻常數調高到大於 system prompt 的值。不採用，因為那只是把常數綁死在目前 system prompt 的長度上，system prompt 一改門檻就再次失效，等於把 bug 藏起來。

門檻常數維持現值不動，語意修正後它才第一次真正生效。

### 保留頭部擴大為開頭連續 system 訊息

「保留頭部」的判定從「僅第一則且其角色為 system」改為「開頭連續的所有 system 訊息」。理由：伺服器每回合把 system prompt 與數則 ephemeral 前言連續放在最前面，它們在語意上同屬不可壓縮前言，用「開頭連續 system」這個結構性條件即可整段涵蓋，而 agent 核心不需要知道呼叫端的前言語意，維持既有的責任邊界。

替代方案是把前言注入改到 compaction 之後。不採用，因為要更動伺服器與 agent 核心的呼叫順序，改動面更大且讓核心耦合到呼叫端的組裝流程。

須留意持久化歷史本身不應以 system 訊息開頭；若未來有此情形，該訊息會被誤判為前言而永久保留。實作時應在該判定處留下註解說明此前提。

### 檔案讀取只回加行號視圖

四個讀取工具都改為對同一份切片只回傳加行號的視圖，沿用專案既有的行號格式（右對齊行號加定位字元），不另創格式。移除原始內容欄位，保留起訖行、總行數與各自既有的識別欄位。

家族範圍以實際稽核加行號輔助函式的呼叫點決定，不以印象認定。四個成員為：工作區的 `read_file`、skill 內檔案的 `skill_read_file`、核心記憶檔的 `memory_read`、知識維基的 `wiki_read`。判準是「回傳一段檔案切片的兩種視圖，且共用同一個工具結果字元預算」。

實際稽核結果（全 workspace `line_numbered` / `region_view` 呼叫點逐一分類）：

| 呼叫點 | 工具 | 判定 |
| --- | --- | --- |
| fleety-tools/src/lib.rs（`ReadFile::call`） | `read_file` | 家族成員，改 |
| fleety-server/src/skills.rs（`SkillReadFile::call`） | `skill_read_file` | 家族成員，改 |
| fleety-server/src/tools.rs（`MemoryRead::call`） | `memory_read` | 家族成員，改 |
| fleety-server/src/wiki.rs（`WikiRead::call`） | `wiki_read` | 家族成員，改 |
| fleety-tools/src/lib.rs（`region_view` 定義與 `edit_file` 的 `applied`） | `edit_file` | 豁免：編輯後確認區域，無並存原始內容欄位 |
| fleety-server/src/skills.rs（`applied`） | `skill_edit_file` | 豁免：同上 |
| fleety-server/src/tools.rs（`applied`） | `memory_edit` | 豁免：同上 |
| fleety-server/src/skills.rs（`UseSkill::call`） | `use_skill` | 豁免：整份 SKILL.md 全文載入，單一視圖 |
| fleety-server/src/tools.rs（`FetchToolResult::call`） | `fetch_tool_result` | 豁免：字元視窗分頁，單一視圖 |

豁免的共同理由是它們都只有一種視圖，沒有可移除的重複；`applied` 三處是編輯後的小範圍確認輸出，`use_skill` 與 `fetch_tool_result` 是全文或分頁載入。

理由：加行號的視圖同時服務兩種用途（讓模型理解位置、讓行範圍編輯可用），而原始內容欄位的資訊完全被它涵蓋。兩者並存等於同一份內容送兩次，在工具結果字元預算固定的前提下直接讓可讀量砍半。只改家族的一部分會讓四個同型工具的回傳形狀不一致，是專案變更完整性規則明文禁止的狀態。

工具說明必須明講行號前綴不屬於檔案內容，讓模型在組 exact-match 編輯的比對字串時知道要剝除。這是本決策唯一的行為風險。

替代方案是保留原始內容而移除加行號視圖（行範圍編輯會變得難用，模型得自己數行），或加參數讓模型自選（schema 變大、多一個概念要教、模型可能兩個都要而回到原點）。兩者皆已評估後不採用。

### 用量型別放在模型回應與回合結果

新增一個描述 token 用量的型別，欄位涵蓋輸入、輸出、總計，以及供應商有回報時的快取命中數。掛在模型回應型別上作為選填，並在回合結果上彙總該回合所有模型呼叫的用量。

理由：選填讓 mock 與 echo 供應商不需改動即可繼續運作；掛在回合結果而不寫進事件流，可避免更動既有事件的序列化結構，也避免舊有持久化紀錄的相容性問題。

三個供應商各自解析原生結構：OpenAI 相容端點的 usage 物件、Gemini 的 usageMetadata、Codex Responses 的 usage 物件，各自的快取欄位命名不同，需分別對應。供應商未回報時該欄位為空，不得以零值偽裝成「用了零個 token」。

### 串流路徑要求供應商回報用量

非串流路徑的回應本體即帶用量。串流路徑預設不帶，需要在請求中明確要求供應商在最終片段附上用量。實作時三個供應商的串流分支都要處理，並在供應商不支援時安靜地讓用量為空，不得因此讓串流失敗。

## Implementation Contract

**In scope:**

1. compaction 的預算語意與前言保留（agent 核心）
2. 四個讀取工具（`read_file`、`skill_read_file`、`memory_read`、`wiki_read`）的回傳形狀（工具層與伺服器層）
3. 三個供應商的用量解析與回合層級彙總（agent 核心）
4. 上述三項對應的規格差異檔與測試
5. 既有離線黃金對話回歸的重跑與必要修正

**Out of scope:** 提案 Non-Goals 所列全部項目。

**Behavior — compaction**

- 一段對話在其可壓縮歷史累積到門檻之前，不觸發壓縮，也不產生額外的摘要模型呼叫。此前的既有行為是超過約十一則訊息就每回合觸發。
- 壓縮發生時，開頭連續的 system 訊息全數原樣保留，其後接摘要，再接最近訊息。當前時間、origin 前言與指令檔前言不得出現在摘要中，也不得消失。
- 完整歷史仍以事件流為準，壓縮只縮小送模型的視圖。此性質不變。

**Behavior — 檔案讀取**

- 工作區檔案讀取的回傳物件包含路徑、加行號視圖、起始行、結束行、總行數；不再包含原始內容欄位。
- skill 檔案讀取的回傳物件包含 skill 名稱、來源層級、檔名、加行號視圖、起始行、結束行、總行數；不再包含原始內容欄位。
- 核心記憶讀取的回傳物件包含檔名、加行號視圖、起始行、結束行、總行數；不再包含原始內容欄位。
- 知識維基讀取的回傳物件包含路徑、加行號視圖、起始行、結束行、總行數；不再包含原始內容欄位。
- 四者的工具說明都必須敘明行號前綴不屬於檔案內容。
- 行範圍切片行為與行號起算方式不變。
- 全文載入型的讀取（例如 `use_skill` 回傳整份 SKILL.md）不在此列：它只有單一視圖，沒有重複可移除。

**Behavior — 用量計量**

- 供應商有回報時，回合結果帶有該回合所有模型呼叫的用量加總。
- 供應商未回報或不支援時，用量為空值，且不影響回合正常完成。
- 用量絕不以零值代表「未知」。

**Failure modes**

- 供應商回應缺少用量欄位：視為未知，不報錯、不中斷。
- 串流供應商不接受「附上用量」的請求選項：串流須照常完成，用量為空。
- 持久化歷史意外以 system 訊息開頭：該訊息會被當作前言保留，屬已知限制，須在判定處註解說明。

**Acceptance criteria**

- agent 核心新增測試：可壓縮歷史小於門檻但前言很長時，不觸發壓縮、不呼叫摘要。
- agent 核心新增測試：壓縮觸發後，開頭多則連續 system 訊息全數原樣存在於結果中，且未被折進摘要。
- 既有五個 compaction 測試須全部通過；若因語意修正而需調整前置條件，調整測試佈置而非放寬斷言。
- 工具層新增或調整測試：檔案讀取回傳不含原始內容欄位、含加行號視圖，且行範圍切片結果不變。既有的「讀取加行號後依行範圍編輯」測試須通過。
- 供應商層新增測試：各自的用量結構能被正確解析；缺欄位時為空值。
- 離線黃金對話回歸須全數通過。
- 全 workspace 建置與測試通過，且不新增 clippy 警告。

**Interfaces touched**

- agent 核心：字元估算函式、保留頭部判定、壓縮進入條件、模型回應型別、回合結果型別。
- 工具層：工作區檔案讀取工具與 skill 檔案讀取工具的回傳 JSON 形狀與工具說明字串。
- 供應商層：三個供應商各自的回應反序列化結構與串流請求參數。

## Risks / Trade-offs

- [壓縮變晚導致 context 變大，小 context window 的本地模型可能超限] → 門檻常數未變，變的只是它不再被 system prompt 淹沒；但實際可壓縮歷史上限確實從「約十一則訊息」放寬到門檻字元數。本次不提供環境變數逃生口（已於提案評估後排除），若實測遇到再另案處理。實作時須在門檻常數處註解說明其語意為「可壓縮歷史的預算」。
- [移除原始內容欄位後，模型組 exact-match 比對字串時可能誤把行號前綴當作檔案內容] → 工具說明明確敘明前綴不屬於內容；編輯工具本身讀的是磁碟上的原檔，比對失敗會回報錯誤而非靜默寫壞。建議實作後以一次真實模型的編輯流程手動驗證。
- [壓縮觸發時機改變，離線黃金對話可能漂移] → 現有黃金案例共十五筆，皆為腳本化的兩則回應短流程，遠低於觸發門檻，預期不受影響；且斷言針對呼叫了哪些工具與最終輸出內容，不針對讀取工具的回傳形狀。仍須實際重跑確認，不得以推論代替執行。
- [用量欄位為選填，呼叫端可能忽略而讓計量形同虛設] → 本次僅要求彙總到回合結果並可被讀取，不強制任何呈現介面。後續的漸進式載入提案應把「能讀到用量」列為其驗收前提。
- [三個供應商的快取欄位命名不一致，可能對應錯誤] → 各供應商分別撰寫解析測試，以該供應商真實回應形狀為準，不共用同一組欄位名稱假設。
