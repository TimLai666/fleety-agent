### Interface and data shape

- Config protocol version is 4.
- Client request: `ProviderModelList { provider: String }`.
- Server result: `ProviderModelListResult { provider: String, model_ids: Vec<String>, error: Option<WireError> }`.
- Model catalog response parsers accept:
  - API: `{ "data": [{ "id": "model-id" }] }`, `{ "models": [{ "id": "model-id" }] }`, or bare arrays.
  - Codex: `{ "models": [{ "slug": "model-id" }] }`, with `id` fallback.
- TUI state uses an in-memory provider-status map and a fetch callback. Credential payloads are not part of either shape.

### Failure modes and fallback

- Missing Provider: server returns an error result and CLI enters manual model input.
- OAuth Provider without usable credentials: server returns an explicit not-signed-in error and CLI enters manual mode.
- Codex catalog non-2xx, malformed JSON, empty catalog, or refresh failure: server returns an error result and CLI enters manual mode.
- Protocol version below 4: CLI does not send the new frame and enters manual mode with an unavailable-version note.
- Credential status query failure: CLI renders `auth=unavailable` and remains editable.
- Any token-bearing server error is sanitized before returning to the client.

### Acceptance criteria

- Regression tests prove the TUI never calls the base URL precondition for `oauth:codex`.
- TUI tests prove signed-in, not-signed-in, and unavailable states render distinctly.
- Protocol tests prove v4 frame serialization and round-trip behavior.
- Server/provider tests prove API and Codex OAuth catalogs return ordered, de-duplicated IDs and sanitize failures.
- Remote config tests prove status and model requests use the existing connection and old protocol falls back to manual mode.
- `cargo fmt --all -- --check`, `cargo test --workspace`, and `cargo clippy --workspace --all-targets -- -D warnings` pass.

### Scope boundaries

In scope are the interactive remote config editor, the protocol capability, server-side provider catalog requests, and regression tests. Out of scope are static catalog maintenance, token transport to the CLI, non-Codex OAuth model discovery, unrelated provider configuration redesign, and non-interactive provider-list status output.

## Risks / Trade-offs

- [Codex backend response shape changes] ? Keep parsing tolerant of `slug` and `id`, test malformed/empty responses, and fall back to manual entry.
- [A protocol bump reaches an exhaustive match that is easy to miss] ? Update all client/server matches and smoke constructors, then run workspace tests and clippy.
- [Credential refresh changes server-side token state during a read operation] ? Reuse the existing `OAuthCodexAuth` refresh path, never return refreshed tokens, and treat refresh failure as a catalog error.
- [A stale status snapshot misleads the user after login/logout in the same editor session] ? Refresh status when a new provider snapshot is loaded and keep auth actions as the authoritative mutation path.
- [Remote model discovery adds latency to the wizard] ? Keep the existing fetch status message and make failures fall back to manual entry without blocking the editor.

## Migration Plan

1. Ship the protocol v4 server and client together. Existing protocol v3 peers continue to edit configuration and use manual model entry.
2. Run unit, protocol, server, CLI, daemon smoke, format, and clippy checks.
3. Manually run remote `fleety config` with one signed-in and one signed-out OAuth Provider, then invoke set-model for each.
4. Rollback is the previous binary pair. No credential file migration or destructive data operation is required.
