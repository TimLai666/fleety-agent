## Context

`context-budget-accounting` 加入的 `measure_harness_footprint` 量出：完整 registry 有 80 個工具、36,927 bytes，加上 59,062 字元的 system prompt，每次請求固定送出約 109 KB（約 27,300 tokens）。工具 schema 是其中最容易收斂的一半。

Fleety 已有兩個同型先例證明代理模式可行：裝置端工具收在 `device_exec` 之後、MCP 工具收在 `mcp_call` 之後，兩者都不展開子工具。skills 也早就是漸進式揭露。本變更把同一原則套用到內建工具。

實作前需要先知道兩件既有事實：

其一，`ToolRegistry::specs()` 回傳全部已註冊工具，沒有任何篩選概念，而 registry 被十餘處建構使用（伺服器、subagent、workflow、eval、daemon）。任何新增的篩選必須預設不改變既有行為，否則所有呼叫端都要同步調整。

其二，也是最關鍵的：agent 迴圈在**進入迴圈之前**只取一次 `tools.specs()` 快照，整個回合沿用。這代表模型在回合中途啟用的工具，在同一回合內不會出現在後續請求裡——模型會搜尋到能力卻無法使用，直到下一回合。不處理這點，整個機制在最常見的情境下就是壞的。

## Goals / Non-Goals

**Goals:**

- 讓開場送出的工具 schema 從 80 個縮到 16 個常駐工具。
- 讓模型能在需要時自行發現並啟用其餘 64 個工具，且啟用在**同一回合內**即刻生效。
- 啟用狀態隨對話持久化，重啟後仍在。
- 對既有的 registry 呼叫端零影響：不設定啟用集合時，行為與現在完全相同。

**Non-Goals:**

- 不改 system prompt 四份文件的內容或分層。
- 不移除任何工具，不改工具行為、參數或風險分級。
- 不改 `device_exec` 與 `mcp_call` 的代理模式。
- 不引入 token 計費或成本換算。

## Decisions

### 啟用集合放在 registry，預設為「全部啟用」

`ToolRegistry` 增加一個可選的啟用集合。未設定時 `specs()` 回傳全部工具，與現行行為逐字相同；設定後只回傳集合內的工具。

理由：篩選必須發生在「模型看到什麼」這一層，而那就是 `specs()`。放在呼叫端各自篩選會讓十餘處建構點各自實作、必然漂移。預設為 `None`（全部）讓 subagent、workflow、eval、daemon 等既有呼叫端一行都不用改。

替代方案是讓伺服器在每次組請求前自行過濾 spec 清單。不採用：`specs()` 的語意就是「模型可呼叫的工具」，把篩選放在外面等於讓這個語意失真，且迴圈裡的風險查詢（`risk_of`）也是查同一份清單，兩邊會不一致。

### 工具呼叫仍以「已註冊」為準，不以「已啟用」為準

`ToolRegistry::call` 維持只看是否註冊。啟用集合只影響模型看得到什麼，不作為授權邊界。

理由：授權邊界已經由風險分級與核可閘門負責，那才是安全機制。把啟用集合也當成授權會產生兩套權限來源，且會在「模型剛啟用、快照尚未更新」的窗口產生偽拒絕。啟用集合是 context 預算機制，不是安全機制——這點必須寫進規格，避免日後被誤用。

### 迴圈每一步重新讀取工具清單

把 `tools.specs()` 從迴圈外移到迴圈內，每一步重新取得。

理由：這是讓啟用「當回合生效」的唯一方法，否則模型搜尋到工具卻要等下一回合才能用，機制形同無效。成本是每步複製一次 spec 清單；本變更之後常駐集合只有 16 個工具，這個複製比現在的 80 個更便宜。

須留意 `risk_of` 也使用這份清單，移進迴圈後它自然跟著更新，是正確的。

替代方案是只在工具呼叫後重新取得。不採用：多一個特例路徑，而每步重取的成本本來就低。

### 啟用以群組為粒度

工具搜尋回傳並啟用整個群組，而非單一工具。群組劃分依實際 registry 內容整理，涵蓋全部 80 個工具、無遺漏。

理由：同一件工作通常需要群組內數個工具（例如瀏覽器自動化必然要導航加截圖加關閉），逐一啟用會產生多次無謂往返。群組是與工作意圖對齊的粒度。

### 啟用狀態隨對話持久化

啟用集合存於對話狀態，隨對話載入與儲存。

理由：一段工作常橫跨多個回合，若每回合重置，模型會反覆搜尋同一個群組，往返成本可能超過省下的 schema 成本。持久化也讓行為可預期。

須留意這會讓長對話的啟用集合單調成長。本變更不處理縮回機制；若實測顯示有必要，另案處理。

## Implementation Contract

**In scope:**

1. registry 的啟用集合與 `specs()` 篩選（agent 核心）
2. 迴圈每步重讀工具清單（agent 核心）
3. 工具搜尋入口與群組定義（伺服器）
4. 啟用集合的對話持久化（伺服器）
5. `protocol.md` 的極短說明段落
6. 對應規格與測試

**Out of scope:** 提案 Non-Goals 所列全部項目。

**Behavior — 開場工具集**

- 新對話的第一次請求，模型看到的工具為常駐 16 個加上工具搜尋入口，不含其餘 64 個。
- 常駐集合：檔案與命令核心十個、skills 兩個入口、核心記憶讀寫兩個、跨裝置兩個入口。

**Behavior — 工具搜尋**

- 模型以能力描述查詢，取得符合的群組名稱、群組內工具名稱與各自一行摘要。
- 查詢命中時，該群組加入當前對話的啟用集合。
- 查詢未命中時，明確回報找不到，且不改變啟用集合。
- 已啟用的群組再次查詢不重複啟用，也不報錯。

**Behavior — 啟用即刻生效**

- 模型在某一步啟用群組後，**同一回合的下一次模型呼叫**即可看到並呼叫該群組的工具。
- 啟用集合隨對話持久化；同一對話的後續回合與重啟後仍然有效。

**Behavior — 對既有呼叫端**

- 未設定啟用集合的 registry，其 `specs()` 回傳全部工具，與變更前逐字相同。
- subagent、workflow、eval、daemon 的行為不變。

**Failure modes**

- 啟用集合含未註冊的工具名稱：該名稱忽略，不報錯（可能來自舊版持久化狀態）。
- 持久化的啟用集合無法讀取或解析：視為未設定，退回全部啟用，不中斷對話。
- 工具搜尋本身永遠註冊於常駐集合，不可被停用，否則模型會失去發現能力的唯一途徑。

**Acceptance criteria**

- registry 測試：未設定啟用集合時 `specs()` 與變更前相同；設定後只回傳集合內工具；集合含未知名稱時忽略之。
- 迴圈測試：某一步啟用新工具後，同一回合的下一次模型呼叫已能看到該工具。
- 伺服器測試：新對話的開場工具數等於常駐集合大小加一；搜尋命中後該群組工具出現、未命中時集合不變。
- 持久化測試：啟用集合寫入後重新載入仍在。
- `measure_harness_footprint` 重跑，開場工具 schema 位元組數顯著低於變更前的 36,927。
- 全 workspace 建置、測試、clippy 無新增錯誤或警告。

**Interfaces touched**

- agent 核心：`ToolRegistry` 的啟用集合存取與 `specs()` 篩選；迴圈取得 spec 的位置。
- 伺服器：工具搜尋工具的 spec 與行為、群組定義表、對話狀態的啟用集合欄位。
- `protocol.md`：說明工具並非全部可見、以及如何搜尋。

## Risks / Trade-offs

- [模型不知道要搜尋，直接放棄某項工作] → `protocol.md` 明講「看得到的不是全部」。這是本變更最大的行為風險，必須以真實模型手動驗證至少一個需要延後工具的情境（例如要求它操作瀏覽器），確認它會先搜尋而非回報做不到。
- [搜尋往返本身也花 token，短工作可能得不償失] → 常駐集合刻意涵蓋最常用的檔案、命令、記憶與跨裝置入口，讓多數對話不需要任何搜尋。若實測顯示某群組被頻繁搜尋，把它移入常駐即可，這是資料驅動的調整。
- [長對話啟用集合單調成長，省下的空間逐步流失] → 接受。本變更的收益在開場與短中長度對話；縮回機制留待實測後另案處理。
- [每步重讀 spec 清單增加複製成本] → 常駐後清單從 80 縮到 17，每步複製比現在的一次複製 80 個更便宜。
- [subagent 仍取得完整 registry，未享受此收益] → 本變更不動 subagent，其啟用集合維持未設定即為全部。這是刻意的範圍限制，可另案評估。
